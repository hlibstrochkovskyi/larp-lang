# LARP 0.2.0-preview.1 — candidate notes

Status: **prepared for review; publication requires maintainer approval**.
These notes describe the next experimental preview. A version string or this
document does not create a tag, assert publication, or replace exact-commit
build and compatibility evidence. See the [publication criteria](../versioning.md#publication-and-evidence).

## File modules

Programs can now span explicitly imported UTF-8 files. An entry imports
libraries with `import "lib/math.larp" as math;`, calls `math::twice(21)`,
and uses types such as `people::Founder`. Libraries declare functions, classes,
roles, and concrete extensions without `main_character`. Only the entry has
that block. Imports execute no initializers.

- Top-level declarations are private by default; `highkey` exports them.
  Exporting a class preserves ordinary constructor/member access rules.
- Aliases have their own qualifier namespace. Each body resolves names and dot
  extensions in its defining file. Imports do not silently add dot extensions.
- Exported extensions support explicit `extensions::train(bro, amount)` calls
  with exact static receiver matching, and first-class references retaining
  receiver parameters and effect bounds.
- Shared dependencies have one nominal identity. Equal names in distinct files
  remain distinct types. Public interfaces cannot expose private nominal types,
  even through nested containers or callback signatures.
- Whole-project type/effect checking, role dispatch, closures, lazy computation,
  and regional scenario specialization use the existing typed IR, mandatory
  verifier, and VM. No host-language translation or text inclusion is involved.

See the [module guide](../modules.md), [RFC](../rfcs/0001-file-modules.md),
[source-unit grammar](../spec/modules.ebnf), and
[implemented feature status](../implementation-status.md).

## Try the extracted candidate

The Linux archive contains `bin/larp`, complete tracked source and documentation,
examples, project fixtures, provenance/checksums, MIT, and Rust runtime notices.
Running the binary requires no Rust installation.

After checking the archive's SHA-256 sidecar and entering its root directory:

```sh
sha256sum -c SHA256SUMS
./bin/larp --version --json
./bin/larp run tests/projects/pitch/main.larp --gc-stress
trial_dir=$(mktemp -d)
./bin/larp build tests/projects/pitch/main.larp -o "$trial_dir/pitch.larpbc"
./bin/larp run "$trial_dir/pitch.larpbc" --gc-stress
./bin/larp fmt tests/projects/pitch/lib/founder.larp --stdout
./bin/larp explain LARP-M006
```

The [pitch project](../../tests/projects/README.md) prints `49`, `20`, and `fr`
on separate stdout lines; `PALANTIR [CrossFilePitch]` reports the trial on stderr.
Its claimed billion-dollar valuation is discarded and selected aura is committed.
One `.larpbc` embeds all checked sources and runs without reopening them.

The new [project execution driver](../../tools/run_projects.py) runs the exact
fixture with the packaged executable in five source/artifact/formatting/GC modes.
Both compatibility hosts must execute it alongside all four legacy conformance
modes. Source snapshots are retained under renamed directories, making original
embedded paths unavailable before artifact execution.

## Changes since v0.1.0-preview.1

- Added source-unit parsing, an injected-resolver import graph, lexical namespaces,
  export/interface checks, filesystem resolution, and multi-source artifact use.
- Added `LARP-M001` through `M007` for resolution, cycles, duplicate aliases,
  entry policy, graph limits, private exported types, and ambiguous exported names.
  Ordinary unknown names, access, type, effect, and region errors keep their codes.
- Text diagnostics now render cross-file related labels against their own source,
  matching the existing JSON source-identity contract.
- Formatting supports import/export declarations, qualified calls/types, and
  library files without an entry block. It formats one file at a time.
- README now has theme-aware logos and an executable pitch example, with expanded
  contributor/development documentation. MIT names **Hlib Strochkovskyi** in full.

## Compatibility and migration

The intended identity is `0.2.0-preview.1`, channel `preview`. The experimental
language baseline remains `0.1`, extended by the module RFC. Artifact writer is
`2`, readers are `1` and `2`; diagnostic and version-info JSON schemas remain
`1`. The driver executes genuine frozen historical artifacts. Those sampled
checks do not promise compatibility with every historical or future artifact.

Existing valid single-file programs retain the legacy grammar, including a local
identifier named `import`. Adding imports or top-level export modifiers selects
source-unit grammar, where `import` is reserved: rename such identifiers when
converting a legacy file into a module. Split programs must move their entry block
to one entry file, mark cross-file declarations `highkey`, and qualify names.
Dependencies are not re-exported; callers need their own direct imports.
Explicit extension receiver selection performs no numeric or class-to-role
conversion; use a correctly typed binding or explicit conversion.

Artifacts do not preserve module privacy as a source-level lookup service:
the whole project is already checked and independently verified. There is no
runtime import resolver or separate compilation. No stable public Rust API,
source compatibility, edition switch, automatic updater, or downgrade promise
is established by this pre-1.0 preview. Retain source and test applications
when updating. See [versioning](../versioning.md).

## Platforms, evidence, and limits

Release candidates target GNU/Linux x86-64, built on Ubuntu 24.04 with official
Rust 1.99.0. The identical archive must execute on Ubuntu 24.04 and 26.04 without
rebuilding. Exact revision, archive/executable digests, preview-document hashes,
and executed legacy/project inventories must agree across both hosts.
See [distribution](../distribution.md), [platform policy](../platforms.md),
and [reproducibility scope](../reproducible-builds.md). Other CPU/OS combinations,
universal Linux compatibility, signing, and publisher attestation are not claimed.

The CLI project root is the canonical entry's parent. Imports remain inside it
after symlink resolution; paths are relative `.larp` files using `/`.
Graph limits are 64 sources, 4096 edges, 4 MiB aggregate UTF-8 text, and 131072
source lines, with existing parser/type/artifact/verifier limits still applied.
Canonical containment is not a guarantee against hostile concurrent filesystem
replacement. Private/generated notes are excluded from release snapshots.

Scenarios remain non-nested with one value-only root. `canon` selects final
field values on normal completion and preserves types, not cross-field business
invariants. External I/O and value escape remain forbidden. VM instruction/frame
limits are finite; there is no VM-wide heap-byte budget or hostile-code sandbox.
See [scenario evaluation](../scenario-evaluation.md) and
[current limits](../implementation-status.md#current-limits-and-conservative-checks).

Packages/registries, re-exports, import cycles, globals/initializers, separate
compilation, user-defined generics, inheritance, async, FFI, general host I/O,
native compilation, debugger, and LSP remain deferred. The
[roadmap](../roadmap.md) and [design review](../design-review.md) remain open.
