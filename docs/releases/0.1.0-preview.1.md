# LARP 0.1.0-preview.1 — candidate notes

Status: **prepared for review; not a published release**. These notes describe
the intended first named preview. They do not establish maintainer design
acceptance, create a tag, or assert that this candidate's exact-commit CI has
passed. See the [readiness audit](../preview-readiness.md) and
[publication criteria](../versioning.md#publication-and-evidence).

LARP is an independent, statically typed experimental language implemented in
Rust. A program is one UTF-8 source file with exactly one `main_character` block.
The real execution pipeline is lexer/parser → name/type/effect analysis → typed
control-flow IR → stack bytecode → mandatory verifier → LARP VM. Programs are
not translated to a host language or interpreted through host `eval`.

## Implemented language subset

- Exact `mf`/`unc` integers, `geeked` floating point, `verdict`, immutable `text`,
  checked integer arithmetic, contextual literals, explicit conversions, and
  `mogg`. There is no implicit truthiness, numeric widening, or null.
- Typed functions, local inference, branches, loops, recursion, first-class
  functions, and contextual/annotated lambdas with immutable snapshot captures.
  Constant conditions select feasible return/initialization paths; dead source
  branches still receive semantic checks.
- Mutable `mfs<T>` arrays with shared identity; fixed `hediJeans<T,N>` arrays with
  element-wise value copying; checked indexing and eager collection pipelines.
  Structural mutation of an iterated array is guarded through aliases.
- Nominal `archetype` objects, checked constructors, public/private members,
  methods, roles with verified dispatch, concrete extensions, and bound methods.
  A tracing collector manages objects, arrays, closures, and lazy cells,
  including reference cycles.
- `baddie<T>`/`result<T,E>`, eager `.copium()` fallback evaluation, `.cope()`
  recovery, `parseScore`, checked `ascend`, and aborting `fraud`. Expected errors
  are values; fatal `crashout` failures have no user catch/recovery mechanism.
- Finite `read`, `write`, `observe`, `io`, and `abort` effect bounds retained
  through callbacks, aliases, closures, bound methods, roles, and bytecode.
- Experimental `larp` regions with `flex` claims, `canon` field selection, and
  `palantir` inspection; memoized SnapshotValue `nonchalant` bindings; dynamic
  `sybau` suppression of `yap` output without erasing effects.
- Explicit host capabilities for `args()` and `readLine()`, with EOF, expected
  input errors, denied capabilities, and resource exhaustion kept distinct.

The [implemented-language guide](../reference.md),
[implementation status](../implementation-status.md), and
[specification](../spec/v0.1.md) define details and restrictions. The specification
remains a design baseline; its existence alone does not assert implementation.

## Try the extracted candidate

From the archive's single root directory, no Rust installation is needed to
execute `bin/larp`. The complete tracked source, examples, and test harnesses are
included. Verify the archive's SHA-256 sidecar before extraction, then:

```sh
sha256sum -c SHA256SUMS
./bin/larp --version --json
./bin/larp check examples/collections.larp
./bin/larp run examples/collections.larp --gc-stress
./bin/larp fmt examples/collections.larp --stdout
trial_dir=$(mktemp -d)
./bin/larp build examples/collections.larp -o "$trial_dir/collections.larpbc"
./bin/larp run "$trial_dir/collections.larpbc" --gc-stress
./bin/larp dump examples/collections.larp --ir
./bin/larp --diagnostic-format=json check examples/hello.larp
./bin/larp explain LARP-T041
```

The collection source and loaded artifact each print `5` and `50` on separate
lines. Artifacts embed source maps and can run without reopening the original
source file. `fmt` preserves tokens/comments, reparses its result, and supports
atomic writes, check mode, or stdout. JSON diagnostics are versioned JSON Lines
on stderr; stdout remains program output. See [diagnostics](../diagnostics.md)
and [formatter policy](../formatter.md).

## Identity, packaging, and platform gate

The intended toolchain identity is `0.1.0-preview.1`, channel `preview`, with
experimental language specification `0.1`. It writes artifact wire version `2`
and reads versions `1` and `2`, always subject to verification. Diagnostic JSON
schema and version-info JSON schema are independently versioned and both `1`.
The version-contract driver executes genuine frozen historical v1/v2 artifacts;
these samples do not prove compatibility with every historical artifact.
See [versioning](../versioning.md) and
[fixture provenance](../../tests/compatibility/artifacts/README.md).

The [platform policy](../platforms.md) requires a native x86-64 GNU/Linux build
on Ubuntu 24.04 with official Rust 1.99.0, followed by execution of the identical
archive on Ubuntu 24.04 and 26.04. Both hosts must pass the archived conformance
and version-contract drivers without rebuilding the CLI. Evidence belongs to
one full source commit, archive/executable digest, and recorded runner images;
previous commits' results do not validate this candidate. No universal Linux,
minimum GLIBC/kernel, other CPU architecture, Windows, or macOS support is
claimed. See [recorded platform validation](../validation-platforms.md).

Packages retain `BUILD.json`, complete payload checksums, the maintainer-selected
[MIT License](../../LICENSE), and upstream runtime notices from the actual Rust
distribution. Checksums identify bytes; they provide no signature or publisher
authentication. Two-build and two-archive byte equality has a defined scope,
not a claim of reproducibility on arbitrary hosts. See
[distribution](../distribution.md) and [reproducible builds](../reproducible-builds.md).

## Known limits and compatibility

- Scenarios have one statically known concrete root whose fields are recursively
  SnapshotValues. No reference graphs, nesting, external I/O, value escape,
  outer mutation, or crossing return/break is allowed. Only normal block
  fallthrough commits selected fields' final values. Fatal failure discards the
  trial; observations remain. Field-wise `canon` preserves types and can violate
  cross-field application invariants; it is not general transactional I/O.
  See [scenario evaluation](../scenario-evaluation.md).
- Default VM limits are 1,000,000 instructions and 1,024 call frames. `--fuel`
  adjusts the instruction budget; it does not bound blocking input or wall time.
  Heap allocation has no VM-wide byte budget; host OOM may abort the process.
  This toolchain is not a sandbox for hostile programs.
- Formatting and embedded artifact source text are limited to 4 MiB. Artifacts
  are limited to 16 MiB encoded and a 64 MiB logical decoder allocation budget;
  the latter is not a process RSS bound. Ordinary source loading is not subject
  to that formatter byte cap. Parser, type, verifier, and module work have
  additional bounds; see [current limits](../implementation-status.md#current-limits-and-conservative-checks)
  and [artifact policy](../bytecode-format-v1.md).
- Input permits 4,096 arguments totaling 1 MiB, physical records up to 64 KiB,
  and 1 MiB consumed input per host. See [host input](../host-input.md).
- Modules/packages, user-defined generics, inheritance, concurrency/async, FFI,
  general host I/O, a native backend, debugger, and editor services are deferred.
  There is no stable public Rust API, source edition switch, or automatic updater.

This is a pre-1.0 preview: source, CLI, runtime behavior, and artifact support may
change with explicit change notes. Retain source and the previous toolchain;
rebuild and test applications when updating. There is no established stable
release to which this first preview promises source compatibility. Open design
findings and later work remain visible in the [design review](../design-review.md)
and [roadmap](../roadmap.md).
